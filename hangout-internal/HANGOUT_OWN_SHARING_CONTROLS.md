# Own sharing controls (strict C3 composition)

This slice supplies a private current-status view and a participant's own, reducing-only **Stop all my sharing** action. It does not qualify an all-ages policy, prove a guardian relationship, approve participation, appoint staff, or enable an identity/provider service. Tests install explicitly synthetic policy and guardian grants; email sign-in is account authentication only.

The routes and controls are available only with the existing strict `HANGOUT_PARTICIPATION_AUTHORITY=c3-v1`, protected beta and `HANGOUT_SESSION_AUTHORITY=lobby-v1` composition. They do not turn those settings on. Ordinary beta operation keeps its existing behavior and has no sharing-controls network requests.

## Caller identity and transaction

`GET /beta/participation` returns only the caller's bounded state, current availability, purpose names, revision and whether an existing record can be stopped. It uses no query parameters and sends `Cache-Control: no-store`.

`POST /beta/participation/stop` accepts only `{ "expectedRevision": <nonnegative integer> }` in a bounded same-origin JSON request. Missing, null and other origins are refused. The gateway constructs the internal request from the actual signed beta cookie; public identity headers, subject/account/principal fields and guardian references cannot select a target.

Inside the actual Lobby native transaction the authority rechecks the active issued SID, invitation generation/version, expiry and current registry profile before and after the record operation. A current verified profile supplies the consent account principal even on an ordinary `/lobby` socket that retains fan role and no room-owner account. This changes no room, staff or moderator powers. A profiled SID with an expired/revoked profile is denied without falling back to an unrelated SID grant. A SID without a profile uses only its own issued guest principal; a replacement SID does not inherit it.

C2 `selfWithdraw` is a distinct participant-authenticated reduction. It does not forge guardian authority. It cancels current pending callbacks, withdraws active receipt usability, clears the subject's purposes/consent references and advances the existing revision. The guardian identity/relationship and originally approved receipt purpose list remain intact. Qualified record-tail bounds still apply. It allocates no missing subject, pending approval, grant or replay slot, and repeating the current withdrawal is idempotent. A valid stored record remains reducible when the policy is inactive or expired; that never makes affirmative sharing available.

## Confirmation and safety

The Lobby serializes withdrawal with its other events. After the reduction commits it refreshes current connections. Fresh writes still recheck C3 in their own native transaction: an effect committed before withdrawal cannot be recalled; an effect ordered after it must be denied. A failed/ambiguous storage write is unconfirmed. A committed withdrawal with failed local refresh is returned as **withdrawn; cleanup unconfirmed**, never represented as a restored grant. A fresh status read can recover the saved permission state after a lost acknowledgement. It cannot by itself confirm live cleanup: the UI keeps that uncertainty in memory and offers an idempotent Stop retry. Only an explicit confirmed cleanup result or the committed socket control clears it; a missing cleanup field is not confirmation.

A fully withdrawn live connection becomes restricted to bounded safety actions on the same server-issued connection and received-message witnesses. It leaves public membership and presence, ends browser media/direct-contact participation, and cannot start chat, a room, media, a provider or staff actions through that restricted socket. During the Stop request, affirmative starter/room/command controls are hidden or disabled while selected report flags and Block/Ignore remain available. **Leave chat** closes this WebSocket once and clears its bounded buffers without revoking the beta sign-in or erasing recorded withdrawal. It remains usable while HTTP is pending and never reconnects automatically. A committed `sharing-stopped` frame ends the browser room/media interface while preserving only its already-received bounded line buffers for selected reporting. The connected visitor can report a previously received line, block/ignore, leave or end the session; expiry/logout clears the local session. This is not an anonymous new reporting grant or a way to inspect additional conversations. Other moderator service access remains separately controlled.

The UI asks for deliberate confirmation. Confirming Stop immediately ends this tab’s media through the existing room/capture-generation fence, before awaiting HTTP. A separate in-memory local pause blocks late room/RTC updates, camera re-enabling and new sharing while preserving the WebSocket and received reportable lines. This is not a claim that server withdrawal or cleanup committed. An error or an authorized status reread never restarts media automatically. The UI shows unknown/expired/pending/withdrawn states and does not persist the private response or poll. It collects no age, birthdate, ID, contact or guardian evidence. Stopping new sharing does not erase delivered messages, remote copies or prior reports. If server cleanup is unconfirmed, local media remains off; retry the narrow Stop request or check the saved state. Close the tab defensively if the browser still indicates capture.

## Integration and rollback boundary

The optional persisted `safetyOnly:true` session row is strictly limited to an empty nick, source, away, memberships and cameras, with PM disabled. Ordinary rows omit the field. Existing Keep-room state compatibility still applies: see [Keep-room sign-in](HANGOUT_KEEP_ROOM_SIGNIN.md).

The `sharing-stopped` media teardown is a current-client protocol. An older browser client can ignore that frame; stopping new server effects alone cannot terminate an already established P2P stream. Activation therefore needs the release owner's qualified current-client/cache delivery and a drain of older live sockets, together with compatible stored-state readers. No mixed-version camera-stop guarantee is established here. A legacy socket-close fallback would need separate qualification because closing the witness also changes connected-session reporting; it is not supplied by this slice.

Explicit known-new initialization or the existing explicit legacy migration writes an optional `participationMode: "c3-v1"` on the strict authority marker when C3 is selected. The marker and current C3 selection must agree in recovery, ordinary authority transactions, direct binding validation and rotation. That durable required-mode latch survives a missing policy: removing the flag cannot activate ordinary sharing. Old unlatched strict domains do not silently opt in to C3; they require the release owner's separately qualified drained mode-admission/migration work. No latch, policy, grant or state repair is inferred or automatically added at startup. Ordinary known-new default markers keep their existing shape.

For older unlatched domains the policy-presence guard still refuses a downgrade. Removing the C3/session-authority flags, including removal of the beta-mode flag as well, also fails closed before any legacy fallback when its strict authority marker or participation policy exists, before legacy initialization or raw-state reuse; a marker-only strict domain is protected too. C3 participates in the recovery configuration snapshot. Re-enable the matching reviewed configuration or use a qualified drained migration; flag removal is not one.

Older strict readers do not understand the optional required-mode marker field or the restricted session row. Preserve the latch when qualifying compatible readers; never strip it as a rollback shortcut. A release owner must preflight stored-state bounds and compatible recovery/rollback readers before activation. Do not reverse the source patch against live restricted rows, delete the restriction to resume sharing, raise caps automatically, or migrate a deployed domain from this guide. The StoryPool deployment owner retains rollout/drain/recovery responsibility; this application slice supplies source and scoped evidence only.

Hosted guardian/policy qualification, actual Access OTP, legal rights requests and deletion/retention decisions remain separate. No production all-ages readiness or deployment is established by these local synthetic fixtures.
