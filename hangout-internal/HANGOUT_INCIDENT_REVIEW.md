# Restricted incident review: local I2 flow

October 25, 2026. This is a usable **loopback-only synthetic fixture**, not a production incident endpoint, legal workflow, real handler appointment or all-ages qualification. It drives the actual lobby engine's delivered-message report and persistence path, then the isolated [I1 case primitives](HANGOUT_INCIDENT_CASE_PRIMITIVES.md). Only fixed benign sample messages are generated; there is no free-text evidence upload, remote fetch, provider, external notification or deployment.

From this application checkout, run `node scripts/preview-incident-review.mjs`, then open `http://127.0.0.1:4397/`. An optional `HANGOUT_INCIDENT_PREVIEW_PORT` changes the port; the bind address remains `127.0.0.1`. Stop with Ctrl+C. Sessions, ordinary fixture reports, case metadata/ciphertext and a separate nonextractable AES-GCM purpose key exist only in this process's memory. A new process starts a new benign demonstration; it cannot recover old evidence and makes no production durability/key-recovery claim. The source/case transaction is staged and serialized across asynchronous callbacks within this single-process adapter.

1. Deliberately choose **Appointed incident handler (synthetic)** and open a local session. The other profiles demonstrate an ordinary moderator/guest without an incident appointment, or another appointed handler without the case ACL. These are explicit role fixtures, not sign-in choices suitable for a public service.
2. Flag one benign sample. This sends `report` through the real `createLobby` engine for a message actually delivered to this connection. The UI reports acceptance only after the engine's persistence completes.
3. Select one current reported source and confirm the displayed synthetic reason/authority/deadlines. Preserve selected report. The request carries only source ID, expected revision/digest, supported case type and the approved reason code; the server supplies deadlines and authority. No button can invent a legal hold or override policy. Opening a case grants only its opener the case ACL.
4. Open the selected evidence deliberately. Text is rendered with `textContent` in a focusable, labelled `<pre>`; there is no HTML, URL preview, image loading or download action. Review, preservation and evidence status remain separate. Mark triaged/close review does not release its hold. A separate release uses only the available synthetic policy decision. An expired release decision is not presented as an available shortcut.
5. Use Disconnect and clear when done. The interface removes known evidence text/DOM and drops selection state, focuses the disconnect status and disables previously detached action controls. A response arriving after disconnect cannot repopulate text. This cannot erase screenshots, independently retained responses or content somebody already read.

## Actual report-source transaction boundary

The fixture injects `persist('moderation-queue', snapshot)` into `createLobby`. That adapter commits the ordinary report snapshot **and** versioned source wrappers in the same transaction domain used by I1 preservation. A wrapper contains immutable message ID, revision, SHA-256, exact selected message bytes, the real report's 24-hour expiry and `reported-public` provenance. The copied bytes omit neighbouring context, IP/device votes, browsing-source data and unrelated messages. They are a reported message, not a legal finding.

Actual engine dismissal and `tick()` expiry persist through that same adapter and remove source wrappers. A copy that commits first remains selected encrypted evidence after ordinary-source dismissal/expiry. A source removal that commits first produces a truthful unavailable/conflict response; no replacement quote is fabricated. No `_debug` map, cached admin report, separate case write or pair of unrelated writes is described as atomic.

The actual engine is itself driven through a bounded serial queue. The shared store bounds transaction admission; sessions are capped at sixteen user fixture identities. Source lists require the current separately appointed incident handler, even before a case exists. Every case/evidence operation still runs I1's appointment/revision/ACL checks. The ordinary moderator does not inherit an incident appointment, and the appointed incident handler is a regular chat participant rather than being promoted to a global moderator. Existing product roles, entry/consent/media protections and operational systems are untouched.

## Authority, transport and clearing

Appointments, local sessions and I1 case/source data share the serialized store. A session is bound to the appointment revision when explicitly opened. Revocation or a newer appointment makes that session stale. The fixture authoritatively resolves the session/appointment again inside I1's operation; supplied principal/role/deadline fields are rejected by the outer adapter. Another appointed handler still cannot read a case without its ACL.

The controller uses a generation guard before dispatch and after asynchronous replies. Refresh invalidates detached old controls and clears displayed evidence; disconnect/revocation clears restricted details and cancels the update subscription. The HTTP launcher sends content-free update/disconnect events through an authenticated same-origin fetch stream; stream end/failure triggers clearing, and action failures also recheck authority. In-process controller tests receive those events synchronously after the revocation commit. Browser clearing depends on receiving the event/network-close signal; it is not an instantaneous remote-erasure guarantee during an unobservable partition. Server authorization stops independently of whether a browser has painted the cleared state.

Loopback requests require the exact Host, same Origin and an ephemeral page CSRF value. Session capabilities stay in client memory/headers, not URLs or browser persistent storage. Fixed asset routes, no-store/no-referrer/CSP headers and bounded request bodies keep this isolated from the public website. Local role selection remains intentionally available to the person running the fixture; this is not real identity or production authorization proof.

## Qualified scheduled cleanup in this fixture

The policy is explicitly synthetic and supplies finite absolute review/hold/evidence/case/tombstone/receipt/audit deadlines. The scheduler arms the next relevant deadline, drives the real engine's source expiry, and runs I1 cleanup only under the separately appointed local maintenance session and current case ACL. It does not release a hold automatically, collect more chat, fetch media or scan private conversations.

An active/overdue hold remains blocked for a qualified human decision; overdue state is shown and is not presented as compliant retention. After approved release/no hold and the evidence deadline, scheduled cleanup removes ciphertext and immutable evidence/source identifiers. Once review is closed and the case deadline is due, it removes the case/ACL and leaves only bounded content-free tombstone/audit/idempotency records until their policy deadlines. Receipt maintenance has its own short synthetic policy receipts. No scheduled mutation on an invalid policy is called successful; fixed error status is shown to the appointed handler. A real service still needs durable cleanup ownership, deadlines/overflow escalation, operational monitoring, backups and approved incident authority.

The policy retains the actual ordinary report TTL of 24 hours. The controller tests inject a deterministic clock and execute the **scheduled callbacks**, rather than reducing production TTLs or claiming a long elapsed browser run. The demonstrated restart creates a fresh I1 model over the same local transactional store and still-live ephemeral key; it does not establish an OS/process restart, Cloudflare hibernation or backup recovery.
