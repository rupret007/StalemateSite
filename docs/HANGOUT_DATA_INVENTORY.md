# Hang Out application data inventory

Source assessment for the shared-community candidate based on `c91c625`, October 25, 2026. This records application behavior and limits, not proof of a deployed revision or infrastructure deletion. New entry badges/readiness work must preserve the distinctions below. Legal applicability and public release remain unqualified; see [privacy and incident handling](HANGOUT_PRIVACY_AND_INCIDENTS.md).

| Data / purpose | Where and who can access it | Application lifetime / limit | Source and caveats |
| --- | --- | --- | --- |
| Nickname and signed device token; local preferences | Browser local storage; same-origin application code | Until cleared/replaced by the visitor/browser; no general automatic storage TTL | `lobby/lobby.js`, `auth.mjs`. Nickname is reusable and token is not account identity. Browser persistence must not be described as anonymous or expiring at logout unless tested. |
| Entry source badge | Current community session, shared message/member display when not hidden | Session context; no independent browsing-history collection | `entry-sites.mjs` and shared-community integration. Allowlisted display context, not a verified visit, identity or authorization. Do not attach undisclosed site names to private incident evidence. |
| Chat/PM display and unsent drafts | Connected tab memory; the intended recipient(s) | At most 300 received lines per channel; leave/reconnect/refresh starts fresh | `lobby/lobby.js`. No chat or PM transcript in browser storage. Pending direct-message metadata is a separate item below. |
| Live moderation buffer | Lobby server memory, accessible to permitted report/moderation paths | Up to 1,000 recent lines overall; room context is bounded to 50 lines | `lobby-core.mjs`. Text and PM data here are not a public backlog; nearby report context is limited further. |
| Delivery receipts | Durable engine state, internal report verification | Up to 1,000 records, 1 MiB and 24 hours; only still-connected recipients retain receipt authority | `message-receipts.mjs`, `lobby-core.mjs`. Content digests plus message/author/recipient metadata, not ordinary plaintext. A digest is still sensitive operational data. |
| Pending/accepted PM consent | Server session state, matching connections | Pending requests expire after 10 minutes; max 1,000 globally and five per sender; real disconnect ends consent | `lobby-core.mjs`. Wake preserves pending metadata, never an undelivered first-message body. |
| Public/PM user-report evidence | Separate staff-only active queue | Up to 100 reports for 24 hours | `lobby-core.mjs`. Exact reported text, nickname, channel, limited context, author-device and reporter references. Ordinary report expiry has no legal-hold exception in current source. Capacity behavior needs explicit intake truthfulness; do not equate a past confirmation with indefinite preservation. |
| Filter-held evidence | Separate staff-only active queue | Up to 100 for 24 hours | `lobby-core.mjs`. Message/reason/author metadata. A restored held message cannot be approved into a different room reusing the name. |
| AI-flagged evidence | Separate staff-only active queue | Up to 100 for 24 hours | `lobby-core.mjs`. Public text, nickname, channel, timestamp, model/category signals. Queue does not prove every message was checked. |
| Private-room staff reports | Separate durable queue; authorized staff only | Up to 100 reports for 24 hours; resolve/dismiss removes active content | `private-reports.mjs`. Explicitly consented selected text/name/reason and opaque room/reporter/target provenance. Quotes remain unverified. No full transcript or automatic nearby context. |
| Private-report retry receipts | Durable internal queue | Up to 200 for the original 24-hour window | `private-reports.mjs`. ID, time, request nonce, digest, status and keyed reporter reference; no quote/name/reason. Full queues reject new intake without silently evicting existing reports. |
| Human moderation action log | Durable log and staff panel | At most 2,000 records for 30 days; scheduled pruning | `community-state.mjs`, `lobby-core.mjs`, `lobby-do.mjs`. Action/nickname/target/reason can be personal or sensitive; not just counts. |
| Ban/mute/kick and abuse state | Durable shared policy records, staff controls | Network bans bounded to 5,000, room bans to 500; some device/account/nickname bans have no automatic expiry; timed IP bans default to one day | `lobby-core.mjs`, `community-state.mjs`. Do not apply the 30-day action-log promise to continuing bans. Daily keyed IP codes are not raw IPs; hosts/providers still process connection data. |
| Rate buckets and aggregate counts | Durable abuse state and count-only staff summaries | Up to 5,000 rate buckets with daily pruning; hourly/count summaries bounded to about 30 days | `community-state.mjs`, `lobby-core.mjs`. Entry-site integrations must not reset community abuse allowances. |
| Registered room and creative state | Durable room records; public directory only where permitted, members/hosts as authorized | Registered names expire after 90 inactive days; temporary rooms after 10 empty minutes; idle activity clears after 10 empty minutes | `community-state.mjs`, `lobby-core.mjs`. Titles/topics/labels/drawings/watch identifiers are user content, despite no saved chat. Up to 400 strokes per room, bounded serialized sizes. Invite keys and WebJam bearer invitations are not saved in room records. |
| Verified owner identity | Shorter verified HttpOnly session; opaque HMAC-derived account in room ownership | Verified session cannot exceed enclosing beta expiry; ownership follows room lifetime | `auth.mjs`, `beta-auth.mjs`, `beta-entry.mjs`. Email is handled by Access and signed identity cookie, not exposed to ordinary visitors. HMAC key changes need migration. |
| Beta admission/session registry | Durable private registry, server authorization | Up to 1,000 sessions; eight-hour expiry and scheduled cleanup, bounded mint-rate state | `beta-session-client.mjs`, `beta-sessions.mjs`. Random IDs, timestamps/revocation, up to 16 hashed private-room references, no chat/media. Cookie invalidation and connected-socket revocation both matter. |
| AI request and quota | Provider receives eligible single public text only; local reserved quota and runtime counters | Local quota is daily; max concurrent work/deadline/backoff; no unbounded backlog or automatic retry | `ai-moderation.mjs`, `ai-eligibility.mjs`. No nick/device/room/history fields in request. Provider retention/child-data configuration is a separately verified dependency, not proved by this table. |
| WebRTC camera/audio | Participating peer browsers; encrypted packets may traverse an enabled relay | No application recording; peer/relay operational handling must be separately assessed | `lobby-room.js`, `room.js`, `turn.mjs`. Local hide or lobby moderation does not erase another participant's copy or terminate every independent native session. Media stays opt-in. |
| YouTube/watch provider access | Visitor browser contacts the chosen provider when loading media | Provider-dependent | `youtube-player.js`, `lobby-room.js`. External connection information/cookies are not the same as local ephemeral chat. Preserve explicit loading choices. |
| Host/CDN/Access/Turnstile logs, SQLite recovery/backups | Infrastructure/provider systems and authorized operators | Not established by application TTLs; deployment owner must inventory actual settings | No physical-erasure or no-logging guarantee is made. Query strings, invitations, JWTs, PINs and evidence must not enter routine logs or analytics. |
| Moderation inbox/appeals, future legal cases | Authorized operators, separately from application queues | No automatic application expiry exists for external inbox records | Agree purpose, access, deadlines and deletion with the operator. No legal-hold or statutory-request workflow is implemented by merely publishing a contact. |

Paths in the table are relative to `hangout-worker/src/` or the private preview asset directory as appropriate. Limits are independently scoped; a 24-hour report TTL does not shorten room ownership, browser storage, provider logs or infrastructure backups.

Before public release, the deployment/legal owners must establish the actual controller/operator, processors and locations; backup/PITR and log retention; consent/parental rights handling; abuse and notice coverage; narrowly authorized preservation; and the source revision that is really deployed. The application session can prepare contracts, UI and tests; it cannot infer these answers from a healthy endpoint.
