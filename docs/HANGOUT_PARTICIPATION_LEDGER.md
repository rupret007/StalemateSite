# Participation consent ledger: inactive C2 foundation

October 25, 2026. This implements storage-injected primitives from [the all-ages design](HANGOUT_ALL_AGES_CAPABILITIES.md), using synthetic authenticated decisions in tests. It is not connected to public enrollment, current beta admission, camera activation, real verification, provider dispatch or any deployment. No legal operator, jurisdiction, guardian verification process or production retention policy has been qualified. All-ages participation remains the objective; this primitive does not establish readiness.

The implementation is [participation-consents.mjs](../hangout-worker/src/participation-consents.mjs); [the tests](../tests/unit/hangout-participation-consents.test.js) use a staged-commit, serializable in-memory adapter. Existing beta age/media/Access/AI protections are unchanged. No contacts, full birth dates, raw identity proof, imagery, emails, chat bodies or browsing-source history are accepted by its schemas.

## Authority and storage contract

Construct `createParticipationConsents({storage, adapters, now, randomRef, limits})` only on the trusted server. Every adapter is explicitly required; missing adapters do not create a permissive fallback. Opaque references are bounded syntax, not proof of randomness, guardianship, authentication or legal adequacy. Production reference generation must be unpredictable and never deliberately reuse an old subject/pending/receipt identifier; the default uses `crypto.randomUUID()`.

`storage.transaction(async tx => ...)` must provide `tx.get(key)` and `tx.put(key,value)` for `participation-ledger:v1`, with serializable cross-instance reads/writes, atomic rollback on failure and durable commit **before its promise resolves**. The module writes one bounded aggregate so subject, guardian, receipt, pending status and callback idempotency cannot commit independently. Adapters may retry the transaction callback against fresh state; it has no verifier/provider calls or external effects. Candidate identifiers are generated before the transaction and reused across retries. An adapter that resolves before durability, shares mutable snapshots, silently loses writes or serializes only within one JavaScript instance does not satisfy this contract.

There is no in-memory authorization cache. Each operation loads and validates current stored state inside the transaction. Missing state permits only explicit policy installation; corruption returns a fixed failure without resetting, logging the record, or repairing it into an authorized state. Unexpected adapter/storage errors produce `unavailable`, without exposing exception text. A rejected or ambiguous commit never returns success. If a write committed but its acknowledgement was lost, retrying the exact callback recovers the established result without a second receipt.

Authentication/verification adapters run **before** the storage transaction. Their results are copied and schema-checked, and their finite expiry plus current policy/subject/guardian revision and pending state are checked again **inside** the queued transaction. This prevents an expired response or a ledger withdrawal/policy change from authorizing after the wait. It does **not** prove an external identity/verifier service stayed authorized between its response and commit. A later external revocation that has not been recorded in the ledger can race a copied response. Production integration needs an approved transaction/commit fence or authoritative revocation protocol; repeating an asynchronous check alone cannot promise an instantaneous cross-service boundary. C3 must qualify that ordering and recheck fresh authority immediately before each controlled effect.

## Trusted adapter results

These are authenticated server decisions, never request JSON or role/age/consent booleans. Proof tokens are passed only to the injected adapter and are not persisted. The adapter must authenticate the caller, bind the exact purpose/request/transaction, check its own revocation state and return the minimum qualified references. The module cannot inspect whether the adapter actually performed those tasks.

| Adapter | Exact successful result / responsibility |
| --- | --- |
| `qualifyPolicy({proof})` | `{config:{policy,rules},expiresAt}` from the qualified policy authority. `policy` uses C1's strict schema; `rules` is below. The module does not decide legal applicability. |
| `authenticateParticipant({proof,purpose:'begin',request})` | `{operationRef,principalRef,communityRef,expiresAt}` for the authenticated community principal and this exact entry operation. A request cannot select a different subject. |
| `authenticateParticipant({proof,purpose:'lookup'})` | `{principalRef,communityRef,expiresAt}` for the current authenticated principal. Do not accept a caller-selected valid subject/binding as authentication. |
| `verifyConsent({proof})` | `{operationRef,pendingRef,subjectRef,principalRef,guardianPrincipalRef,decisionRef,verifierRef,status,purposes,verifiedAt,expiresAt}`. `status` is `approved` or `declined`. This decision must independently establish the guardian relationship, approved verification route and specific consent for the pending subject/purposes/notice; knowing a reference is insufficient. |
| `authenticateGuardian({proof,request})` | `{operationRef,subjectRef,principalRef,guardianRef,guardianRevision,expiresAt}` for the current authenticated guardian and rights request. The ledger additionally checks its own verified relationship/revision/deadline. A room owner, moderator, matching email or source badge is not this authority. |

The ledger's verified guardian record is a restricted reference to the authenticated guardian principal, subject, verifier and decision, with revision and expiry; it contains no verification transcript or contact. It does not grant staff or incident-review powers. Reverification/recovery of an expired guardian relationship and complete parental access/deletion/dispute handling remain qualified workflow work, not a new route supplied here.

## Minimal stored records and finite deadlines

All schemas are version 1 with exact own data fields, bounded reference/list counts and safe integer timestamps/revisions. Unknown fields, extra collection, accessors, duplicate/unknown purposes and unqualified proof-shaped booleans are refused. References, consent metadata and idempotency signatures are still sensitive pseudonymous data, not anonymous statistics. Store access must remain restricted; no ledger contents belong in People, public chat, directory, broad staff broadcasts, analytics or ordinary logs.

| Record | Purpose and deletion boundary |
| --- | --- |
| Current subject | C1-compatible subject/principal/community/policy/notice/revision/state/purposes/receipt references, plus `deleteAt`. Active permission ends at its explicit expiry; ordinary retained state ends under the policy-supplied subject tail. |
| Guardian authority | Subject/guardian-principal/verification decision references, revision/state and explicit expiry; a separate finite guardian tail bounds retained proof metadata. |
| Consent receipt | Subject/guardian/policy/notice/verifier/decision references, original explicit purposes, revision/status and issued/expiry/deletion times. Current-purpose narrowing does not rewrite the original consent as a new approval. Withdrawal changes its status and may shorten its remaining deletion deadline. |
| Pending transaction | Server-created random reference bound to subject/principal/current revision/policy/notice/allowed verifier/purposes; finite pending and grant deadlines, terminal status and callback deletion deadline. No real guardian contact or pending contact store exists. |
| Callback idempotency | Bounded `begin`/`complete` operation reference, exact request/decision tuple, current-state result and finite deletion deadline. It excludes the proof token and raw evidence. A historic success is refused as `superseded` after current state/revision changes. It is not an immutable legal audit or rights-notice receipt. |

`rules` has exact fields `version`, `verifierRef`, `pendingMs`, `grantMs`, `subjectTailMs`, `guardianTailMs`, `receiptTailMs`, `callbackMs`, `operationMs`. Every duration is a positive finite safe integer, deadline arithmetic must remain safe, and `pendingMs < grantMs`. These are required policy inputs, not chosen legal defaults. Grant/pending deadlines are capped by the policy's own expiry. A retry does not extend the original pending, grant, receipt or subject-retention deadline.

The structural upper bounds are 64 subjects, 128 guardian references, 256 receipts, 128 pending transactions, 256 callback idempotency records and 1 MiB total. Tests can inject smaller bounds. These are foundation ceilings, not production sizing, legal retention periods or evidence that this service can safely support a public audience at those numbers. Growth refuses atomically when a bound is exceeded, preserving accepted records. No unexpired receipt is evicted to accept another consent. Small per-subject byte headroom is reserved before growth for bounded withdrawal state/revision updates.

`sweep()` expires pending/active grants and verified guardian authority, then deletes records whose explicit `deleteAt` has arrived. Lazy checks also stop expired authority, but this module installs no scheduler. The receiving service must run and monitor cleanup at the qualified deadlines, handle ambiguous cleanup honestly, and reconcile backup retention/deletion. Missing/malformed rules or corrupt state do not create an implicit infinite-retention policy or authorize a reset; they require the owning operator to resolve the failure.

## Operations and ordering

| Method | State transition and result |
| --- | --- |
| `installPolicy(proof)` | Installs the trusted qualified/unqualified policy and retention rules atomically. A higher monotonically increasing policy revision invalidates authorized/pending subjects, active receipts and pending callbacks. Lower revisions and changed contents at the same revision are refused; withdrawn subjects are not reactivated. Installation is not permission to publicly enable collection. |
| `begin(proof,{expectedRevision,purposes})` | Finds the authenticated principal's current subject, or creates a server reference at expected revision `0`. A matching current revision is required for replacement. Moves to `pending`, with no publishing/media/provider purposes, cancels superseded pending work and retires old active grants. Returns the caller's pending reference only after commit. |
| `complete(proof)` | Rechecks the authenticated decision against the current pending subject/revision, current policy/notice and permitted verifier/purposes/deadlines. Approval atomically creates guardian+receipt+authorized subject+callback result; decline grants nothing. A verified decision cannot be reused for another pending transaction. A different or out-of-order callback cannot promote a completed/cancelled/withdrawn transaction. |
| `change(proof,{expectedRevision,purposes})` | Authenticated guardian reduction only. Nonempty purposes must narrow the current authorized grant; `[]` withdraws, increments revision, cancels pending work and retires active receipts. A matching repeated reduction acknowledges only the current established state, without extending a deadline or allocating an intake/callback slot. Older wider requests cannot restore removed purposes. Policy inactivity does not become a new prerequisite for withdrawal. |
| `lookup(proof)` | Loads a fresh policy/current subject for the authenticated principal only, checking the current receipt/guardian relationship for an authorized state. Returns internal frozen C1 projections, never guardian records or raw receipts. It does not sign a browser session or provide a reusable authorization grant. |
| `sweep()` | Internal bounded cleanup with content-free counts after successful transaction; no public maintenance endpoint is added. |

CAS and transaction ordering are observable: a withdrawal/policy change that commits before the callback's transaction prevents approval. If approval commits first, a later withdrawal invalidates it with a newer subject revision. A failed/ambiguous withdrawal is reported as unconfirmed, never as success. Callers must not keep acting on cached authority after such a failure; actual session shutdown, durable retry/fan-out and provider dispatch barriers are C3 work.

## Test evidence and remaining contracts

The synthetic suite covers delayed durable commit; rollback and committed-but-lost acknowledgement; independent-instance duplicate/competing callbacks; mismatched/late/reused/out-of-order decisions; withdrawal during verifier authentication; expired authentication inside the storage queue; monotonic policy invalidation; purpose narrowing and failed withdrawal retry; pending/active expiry; bounded deletion; count/byte capacity preservation and withdrawal headroom; isolated input/output aliases; forbidden extra collection; and corruption without reset. C1 tests separately verify the resulting purpose/revision/authority intersection.

This proves application primitives against the injected test-store contract, not Cloudflare SQLite durability, deployed identity revocation, real guardianship, verifiable parental consent, legal compliance or public all-ages readiness. Still required: qualified operator/jurisdiction/audience and pre-consent infrastructure decisions; a real approved authentication/guardian/verification/rights process; authenticated same-community session integration; reviewed storage binding/transaction/backup/anti-rollback behavior and cleanup ownership; authoritative C3 effect/revocation fences; narrow incident preservation; accessible hosted journeys. Restoring an older entire ledger snapshot can restore older approvals unless the recovery owner first reconciles later withdrawals/deletion records; a snapshot's internal revision alone cannot detect that rollback. No deployment, shared operations, purchases or provider calls are performed by this slice.
